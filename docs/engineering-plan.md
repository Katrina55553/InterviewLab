# AI-Meeting 工程化设计在 Python 平台中的实施方案

状态：工程化实现 v2；更新日期：2026-10-20。P0–P4 已落地，P5 已加入隔离双实例故障、容量与浏览器 CI、不可变制品发布及回退门禁。实际运行证据与未验收项见 [verification.md](verification.md)，启动、队列、故障与密钥手册见 [engineering-operations.md](engineering-operations.md)。真实供应商及生产/预生产发布回退仍须在对应环境验收，不能以测试供应商替代。

## 1. 目标与边界

在现有业务闭环上补齐可控制、可观测、可验证的工程能力，学习 AI-Meeting 的调用治理、资源隔离、分布式协调和恢复设计。

- 保留 FastAPI、LangGraph、Celery、PostgreSQL、Redis 和现有前端；保持简历诊断、面试、聊天与管理员入口。
- PostgreSQL 继续保存权威业务事实。Redis 故障时，已有问题、答案、评分和报告仍可读取；异步任务等待 Broker 恢复。
- 沿用命令 ID、状态版本、题目 ID、会话与资源归属检查；恢复读取与报告读取不调用 AI。
- AI 结果未知必须单独记录，用户确认后才能创建新尝试；规则结果只允许用于显式演示模式。
- 本轮不恢复 RAG，不增加题库或可视化工作流编辑器，不拆微服务，不引入另一套工作流状态库。
- 改动使用增量 Alembic 迁移，保留当前平台记录；不执行 `reset-dev`，也不安排旧版业务数据迁移。
- AI-Meeting 目录只作参考，所有实现与测试落在 ResumeAgent。

完成后的标准是：供应商故障、流量过载、重复任务、进程退出和 Redis 丢失都有明确行为，并能通过独立进程实验与运行指标验证。

## 3. 模块边界

按阶段逐步提取模块，不先做全目录搬迁。保留当前 `api.py`、`auth.py`、`chat.py`、`media.py` 等路由入口；`service.py`、`runtime.py` 在过渡期转调新模块。

```text
backend/app/platform/
  contracts.py                 # 命令、事件、错误、调用上下文
  domain/                      # 面试状态转换、追问与评分规则、快照校验
  application/                 # 命令、查询、准备/报告、恢复服务
  persistence/                 # PG 仓储、短事务、租约及条件提交
  ai/                          # 供应商适配、准入、Guard、Flight、工具执行
  operations/                  # 日志、指标、就绪检查、巡检
  models.py / media_models.py  # ORM 映射继续由 Alembic 管理
```

依赖方向：路由适配器 → 应用服务 → 领域规则和持久层；应用服务经 AI 网关调用供应商。领域规则只接收数据并返回决策，不导入 FastAPI、ORM 或 Redis。只在需要替换外部边界时定义接口，避免为每张表建立空泛的抽象层。

## 4. 一致的错误与追踪协议

- 保留业务 `request_id`；新增由服务端生成的 `trace_id`，贯通 HTTP、WS 命令、SSE、outbox、Celery 和 AI 子调用。
- WS 每个命令有独立追踪上下文，连接本身另有连接 ID；内部异步任务继承追踪上下文，不把浏览器提交的追踪头当可信身份。
- 错误统一为 `code`、`message`、`retry_policy`、`outcome`、`trace_id`；REST 保留 HTTP 状态，WS/SSE 使用相同错误对象。
- `retry_policy` 为 `never / manual / automatic`；`outcome` 为 `not_sent / known / unknown`。明确允许自动重试的内部操作才能使用 `automatic`。
- 前端兼容旧错误字段一个过渡阶段；事件唯一 ID、序号和命令去重语义保持不变。

| 错误 | HTTP | 预期处理 |
| --- | --- | --- |
| `STATE_CONFLICT` / `IDEMPOTENCY_MISMATCH` | 409 | 刷新快照；禁止把原请求 ID 换成另一份内容 |
| `AI_QUOTA_EXCEEDED` | 429 | 显示限额；不调用供应商 |
| `AI_OVERLOADED` / `AI_CIRCUIT_OPEN` | 503 | 保留答案；明确本次未发送，可稍后手动重试 |
| `AI_TIMEOUT` / `AI_RESULT_UNKNOWN` | 504 / 503 | 保留节点进度和答案，提示外部结果可能未知；手动创建新尝试 |
| `AI_CONFIGURATION_ERROR` | 503 | 提示管理员处理；不循环重试 |

日志只记录阶段、状态、耗时、错误码与内部关联 ID；不输出密钥、Cookie、完整请求体、简历、回答或模型响应。`request_id`、用户 ID、面试 ID、动态 URL 不作为指标标签。

## 5. AI 调用治理与资源隔离

### 5.1 调用顺序与失败边界

调用流程：身份与归属检查 → 命令认领 → 节点结果复用 → 限长等待 → 熔断检查 → PG 准入与配额预留 → 供应商调用 → 保存调用结果 → 节点检查点 → 业务条件提交。

- 整个流程有单调时钟截止时间；排队、供应商 I/O 和工具调用使用剩余预算，不能各自重新获得完整超时时间。
- 使用 PG 短事务为每次实际调用预留请求次数与 Token 预算；输入预算加本次最大输出上限必须在发送前获准。得到可信用量后结算，未知用量保守保留预留并单独核查；不能只统计已完成调用而让并发请求透支额度。
- 命令租约在排队和执行期间续期；任何写入仍检查 owner、未过期租约和状态版本。失去租约后停止后续节点并丢弃迟到写入。
- 每次供应商请求都有独立尝试记录。已确定的模型结果先保存，再推进节点和业务状态；二者间退出时可以复用已知结果。
- SDK 默认关闭隐藏重试。超时、连接中断和不确定的供应商错误不自动重发；供应商明确拒绝的情况也需按适配器证据分类，不能仅凭 HTTP 5xx 推断未执行。
- 自动重试用于幂等的内部读操作、可重新派发的任务和未发送前的基础设施操作，并设置次数、退避及总时间预算。

### 5.2 熔断策略

v1 按进程、供应商、模型和凭据修订维度维护熔断器；这是明确的作用域，不宣称集群共享熔断状态。全局并发由 PG 准入限制保护。

初始可调参数：最近 20 次请求中至少 10 次完成后统计；可归因于供应商的失败达到 50% 时打开 30 秒；半开只允许 1 次探测。配额不足、用户取消、解析校验失败和本地过载不计入供应商失败率。参数是压测起点，需通过故障实验调整。

### 5.3 并发与等待

- 分为交互面试/聊天、准备/报告、视觉三类预算；后台报告和视觉不能耗尽交互预算。
- 按供应商实际凭据作用域设置共享并发上限，避免多个配置项引用同一 API Key 时绕过限制；作用域使用服务端生成的不可逆标识，不暴露密钥。
- `platform_ai_permits` 通过 PG 短事务原子认领有租约的许可，数据库时间判断过期；事务结束后再调用 AI。释放与续期校验 owner；不在等待供应商期间持有数据库行锁。
- 另设进程内并发与等待人数上限；队列已满立即返回 `AI_OVERLOADED`，等待超过预算也退出。Redis 仅加速通知，不决定是否拥有许可。
- 正常租约下全局有效许可数不超过配置上限。许可到期可回收，但不能保证远端已停止，因此不承诺供应商实际在途请求的绝对上限；未知调用单独计数。出现集中未知结果时停止增加新尝试并触发告警。
- 工具使用独立的小额并发预算。嵌套 `verify_code_snippet` 不等待其父调用占有的同一许可；由父调用交接许可后执行子调用，再重新准入下一次供应商请求。保留 `AI_MAX_CONCURRENCY=1` 的死锁回归。

### 5.4 Worker 与媒体

- 准备和报告仍是持久任务；生产分别由独立 Celery Worker 消费 `prepare`、`report`，保留 `default` 处理过渡期已发布任务。最小开发配置可由一个 Worker 消费全部队列，但要标明不提供资源隔离。
- 本地解析放到有界进程池；AI I/O 使用异步客户端，不把 CPU 解析放进 Web 事件循环。先隔离现有任务，后续再按压测结果决定是否拆更多任务。
- 初始使用 `worker_prefetch_multiplier=1`，结合 late ack 和数据库任务认领；它限制预取，不代表任务恰好执行一次。长短任务独立路由依据 [Celery 官方优化说明](https://docs.celeryq.dev/en/stable/userguide/optimizing.html)。
- ASR 的连接数、音频有界队列及清理单独限制；TTS 查询/下载有超时和并发上限；视觉保持 5 秒节流、一个请求在途，并优先拒绝过载视觉请求。

## 6. AI 调用级 Single-flight

当前命令幂等继续作为业务入口。新增 Flight 用于同一逻辑节点的调用协调和已知结果复用，不做跨用户内容缓存。

- Flight key 包含用户、资源、逻辑操作、节点、输入摘要、冻结配置指纹和快照版本。摘要在服务端生成，禁止只以简历文本或回答内容作为共享键。
- 逻辑操作 ID 由应用服务分配，节点重试显式关联原操作；结果未知后的人工重试增加尝试代次，保留原 Flight 和尝试记录。只有输入、配置与版本全部相同的已知成功结果可复用，不能靠忽略 request_id 的内容哈希盲目合并新命令。
- 同一个 key 只有一个 owner；follower 通过 Redis 通知加 PG 轮询等待。通知丢失不影响正确性，等待者有自己的截止时间。
- `platform_ai_flights` 保存逻辑 key、状态、owner、租约、已知结果与错误分类；`platform_ai_calls` 保存每次实际尝试及用量。只有 owner 占用供应商许可与调用配额。
- 已知成功结果经结构校验后持久保存，再通知 follower；成功写入使用 owner/租约条件。历史业务评分继续保存在面试事实中，不能因 Flight 清理而消失。
- 若进程在供应商响应后、结果保存前退出，状态为未知；租约到期不会自动调用供应商接管。用户明确重试后创建新尝试，审计关联上一次未知记录。
- SSE 聊天维持已有消息与部分内容保存方式；Flight 复用不把半段流当完整成功，也不把普通聊天转换成先生成后播放。
- v1 不添加 L1 内容结果缓存；完成实际命中率与数据库读取测量后再决定是否需要。

业务结果只接受一次提交；外部请求可能重复计费的边界保持明确。

## 7. 状态、异步任务与配置历史

### 7.1 状态与恢复

- 提取纯函数状态转换规则，覆盖 ready、active、reporting、completed、failed 与各命令合法组合；LangGraph 负责节点编排，规则负责是否允许推进。
- 快照新增 `schema_version`，与并发控制的 `version` 分开。兼容读取现有快照，未知新版本只读拒绝或明确报错，不调用 AI 修补历史。
- 修正启动迁移检查硬编码 `20261015_0001` 的方式：从当前发布包的 Alembic head 校验数据库，保证新增迁移后应用能正确启动。
- 独立巡检进程扫描失去租约的命令、任务、许可和调用；其操作只做状态标记、告警和确定安全的修复，不自动补算未知 AI 结果。

### 7.2 Outbox 与 Broker 恢复

- 区分业务任务执行状态与投递尝试，增加投递时间、下次投递时间、次数、认领者及认领租约。
- dispatcher 短事务认领、事务外发布、条件确认；发布超时视作投递未知，允许再次发布同一个逻辑任务，消费者始终通过 PG 认领。
- 已标记 published、仍未被消费的任务可能因 Broker 数据丢失而消失。巡检依据数据库任务状态重新派发；queued 可重派，running 且过期转 unknown，completed 永不重算。
- 新增投递尝试关联 ID，保留原始逻辑 job ID；不能用 Celery task ID 当唯一正确性保障。
- Worker 抢占后、AI 调用前和调用后分别注入故障，验证重新派发不会绕过命令及节点调用账本。

### 7.3 配置修订与运维策略

- Provider、Agent 新增不可变修订记录，包含实体 ID、版本、操作人、时间、配置及删除标记；更新与修订写入在同一事务，使用预期版本防止覆盖。
- 管理员可分页查看修订与脱敏差异；密钥始终加密，审计响应不回传密文或明文。初始迁移只建立当前版本基线，不伪造历史修改记录。
- 恢复旧配置通过创建新版本完成，不修改已有修订或既有面试快照；不自动回退模型。
- 提示词、工具和模型内容配置随面试冻结。紧急停用、全局容量和配额属于实时运维策略，每次新 AI 调用重新检查；停用不改写历史结果。
- 设置稳定随机 `SECRET_KEY`，生产配置缺失或仍使用示例密钥时启动失败；更换密钥需要明确的重加密步骤，不能静默覆盖旧凭据。

## 8. 可观测性与健康检查

- JSON 结构日志贯通 trace、命令、任务、Flight 与 AI 尝试；错误记录分类及异常栈，敏感内容过滤在统一出口执行。
- 指标覆盖：调用数量/耗时/失败分类、准入等待与拒绝、活跃许可、熔断状态、Flight 合并命中、未知结果、租约丢失、outbox 最老等待时间、任务排队/执行时间，以及媒体队列背压。
- 标签只用有限集合，例如 scene、工作负载、结果类别、服务角色；供应商实例及模型若开放任意配置，需要限制标签集合或改用日志检索。
- `/health/live` 只判断进程存活；`/health/ready` 检查 PG、迁移版本和本角色必要依赖；保留 `/health` 兼容已有入口。探针不调用 LLM、讯飞或视觉供应商。
- backend 在 Redis 故障时返回带能力状态的 degraded，就绪判断仍允许事实读取；Worker 与 dispatcher 的 Broker 不通时报告该角色未就绪。PG 不可用时业务就绪失败。
- 同时覆盖启动时 Redis 已不可用的情况：Web 初始化降级后仍可读取 PG 事实，异步能力显示排队或不可用；恢复 Redis 后重连并由巡检修复待派发任务。
- dispatcher、Worker 用实例心跳与最近成功进度判断健康，不能用“集群中任意一个 Worker 能 ping”代替本实例健康。
- 指标只走内部监控网络；业务 Nginx 不公开代理 `/metrics`，管理员诊断接口另做鉴权和脱敏。
- 先使用每容器一个 Web 进程、横向多实例，Worker 父/子进程指标分别正确汇总；引入 Prometheus Python client 时验证 prefork 生命周期。其多进程模式有专门限制，不能把普通单进程计数直接视为全局数据，见 [官方多进程说明](https://prometheus.github.io/client_python/multiprocess/)。

交付基础看板与告警：供应商失败/超时、过载、未知结果突增、outbox 堵塞、Worker 心跳缺失、PG 不可用。阈值在压测后确认；告警文本不携带用户内容。

## 9. 分阶段交付

| 阶段 | 改动范围 | 独立验收 |
| --- | --- | --- |
| P0：契约与基线 | 错误契约、trace 上下文、迁移 head 校验、当前行为回归、基准负载脚本 | REST/WS/SSE 错误语义一致；新增迁移可启动；旧快照读取不调用 AI |
| P1：治理与隔离 | Guard、限长等待、总时间预算、PG 许可、配额、熔断、工具预算 | 过载立即拒绝、故障打开熔断、半开探测；双实例共享并发受限；嵌套工具不死锁 |
| P2：持久调用协调 | Flight/尝试账本、已知结果先保存、follower、未知重试 | 相同节点只接受一个结果；Redis 通知丢失可读回；未知结果不自动重发 |
| P3：任务与历史 | 队列/Worker 隔离、outbox 派发修复、巡检、状态规则、快照版本、配置修订 | Broker 数据丢失后 queued 任务可重派；completed 不重算；修订可查询，面试冻结不变 |
| P4：运行可观测 | 指标汇总、看板、告警、组件就绪、私有诊断 | 双实例计数正确；能从 trace 找到任务与调用；故障告警触发且无敏感内容泄露 |
| P5：故障与交付 | 真实进程故障脚本、浏览器 CI、负载测试、生产发布门禁和回滚演练 | 从空环境构建启动；双实例故障矩阵通过；测试的镜像与部署镜像一致 |

P0 即加入基本日志与关联 ID，P4 完成指标与运行看板；P1、P2、P3 每阶段都运行对应真实数据库故障测试。模块提取随阶段进行，每个阶段保持可启动和可回退。

## 10. 验收矩阵与发布门禁

### 10.1 独立进程故障实验

测试环境为真实 PostgreSQL 16、Redis 7、两个 backend、独立 dispatcher 与 Celery Worker，使用隔离数据库/卷。可控供应商服务记录调用次数与故障时机，只用于协议和可靠性实验；真实供应商另行验收。

| 注入场景 | 必须满足 |
| --- | --- |
| 两实例相同 request_id、不同内容复用 ID、不同 ID 回答同一题 | 一个业务结果；错误内容拒绝；竞争者冲突 |
| 调用前退出、调用中 kill、调用返回后但保存前退出 | 能区分未发送、已知、未知；不会把未知状态伪装成评分 |
| Flight 结果保存后、业务提交前退出 | 重启后复用已保存结果，不重复调用已知节点 |
| 租约过期后旧实例恢复并写入 | 条件提交失败，不能覆盖新状态或释放新 owner 的许可 |
| Redis 停机/重启/清空测试库，通知丢失 | 事实读取一致；queued 任务恢复派发；不自动接管未知 AI 调用 |
| 发布后确认前退出、Broker 清空、Celery 实际重复投递 | 重复任务不重复接受结果；数据库未完成任务不会永久卡在 published |
| 上游持续失败、长时间无响应、请求洪峰 | 总预算生效、队列有上限、熔断可恢复，普通读取仍可用 |
| WS/SSE 断开、麦克风拒绝、媒体失败、页面离开 | 文本流程可继续；部分内容保留，设备与后台请求清理 |

故障脚本必须等待明确检查点后再终止进程，保存进程、数据库断言及脱敏调用计数证据；不能只以 sleep 推测故障发生位置。破坏命令仅作用于测试 Compose 项目及测试数据库。

### 10.2 检查与性能目标

- 后端 Ruff、Pytest；前端 ESLint、TypeScript、Vitest、生产构建。发生前端变更时同步提交 `frontend/dist/`。
- 将 Playwright 纳入依赖，CI 启动完整测试栈、迁移、显式演示 E2E 与管理员 E2E；失败保留脱敏日志与截图。
- 负载脚本区分正常供应商延迟、慢调用和故障；记录吞吐量、P50/P95/P99、内存、DB 连接、队列长度及拒绝率。
- 初始目标：已满队列的拒绝 P95 小于 500ms；供应商故障期间登录与历史读取 P95 相对基线劣化不超过 20%；数据库连接、内存和队列始终受配置上限约束。目标在记录硬件、并发和数据规模后验收，不提前宣称容量。
- 对 LLM、ASR、TTS、视觉逐一记录真实凭据联调结果；无凭据时标为未验收。可控供应商测试通过不替代真实服务通过。

### 10.3 发布与回滚

- CI 构建带提交 SHA 的不可变镜像，部署使用本次通过 CI 的 SHA/镜像摘要，避免拉取时变成另一版本。
- 生产缺少必要配置时直接失败，不从 `.env.example` 自动创建配置。先验证配置和迁移兼容性，再替换应用。
- 使用向后兼容的增量迁移；破坏性迁移单独安排。升级前备份，应用回退保留兼容 schema，不自动执行数据库降级。
- 移除“健康检查超时仍显示部署成功”的行为。检查 Web、Worker、dispatcher 与任务完成探针；失败保留证据并返回失败状态。
- 在预生产演练回退到上一镜像；明确 Compose 单机更新可能有短暂停机，不承诺零停机。
- 提供真实启动命令、队列说明、配置表、故障手册、备份恢复和本阶段与 Java 的对照文档。

## 11. 实施顺序与范围控制

建议按 P0 → P1 → P2 → P3 → P4 → P5 推进，每阶段用独立 PR 或提交组交付。先完成一条真实面试命令的治理与故障闭环，再推广到聊天和媒体，避免同时改写所有入口。

第一批具体工作是：补动态迁移检查和错误/追踪契约，建立不调用真实供应商的基线与故障可控端点，随后实现限长等待、供应商许可与熔断。真实凭据联调可在上述工程阶段之外独立进行。
